01 / FROM INTENT TO A MODELWho can act, when, and what changes.

Less room
for guesswork.

Requirements written in English can leave decisions open to interpretation. Agents can fill those gaps with assumptions.

Meant gives you a small, clearly defined language for describing intended behavior: who can act, under what conditions, and what changes. Your team makes those decisions explicit, giving agents less to guess.

“Send the invoice”
leaves a lot unsaid.

Who can send it? What if it is empty? Can it be sent twice? An agent needs these decisions before it can build the behavior you intended.

Here, the model says when SendInvoice is allowed and what it changes. Storage, API routes, framework, and deployment belong to a separate engineering design.

Explore the complete model ↗
Sending an invoice
concept Invoice
  dimension status = draft | sent

concept DenyCode
  field copy: string
  values
    NOT_DRAFT "Only a draft invoice can be sent."
    EMPTY_INVOICE "An invoice needs at least one line item."

shape Draft of Invoice
  where status = draft

shape Empty of Invoice
  where no LineItem

action SendInvoice of Invoice
  by owner
  requires Draft else NOT_DRAFT
  requires not Empty else EMPTY_INVOICE
  effect
    status = sent

02 / THE ENGINEER’S CHOICESThe invoice rules stay the same.

Choose how
to build it.

The same invoice rules can work in a small application or an existing system. Choose a design below to see what an engineer might build.

The business contractAgreed behavior

When can an invoice be sent?

  1. Only the owner can send it.
  2. It must be a draft.
  3. It must contain at least one line item.
  4. Sending it changes its status to sent.

Changing the framework or database leaves these four rules intact.

03 / BUILT FOR PEOPLE AND AGENTSDraft, review, implement, test.

From agreed rules
to application tests.

01

Agree on the behavior

Product managers and engineers decide the rules, exceptions, and outcomes in the business’s own words.

02

Check the model

An agent drafts the model. Deterministic checks catch structural mistakes. Simulation explores supported claims and can expose counterexamples.

03

Choose the implementation

The engineer chooses the architecture, stack, and integrations. Agents work from those decisions and the agreed model.

04

Test the application

Test that the application behaves as agreed. Review changes to the requirements before asking an agent to implement them.

How it works →
Install, then prompt your agent
bun add -g meant-lang
Then give your agent one prompt that names one workflow:
Run `meant` and follow its instructions to build a Meant model of the <workflow> workflow in this app.

It reads that workflow's code.

Permission checks, stored entities, status fields, handlers, guard clauses, and tests become declarations, each citing the file and line it came from.

It proposes; you decide.

New vocabulary waits for your verdict, and contradictions in the code are marked as undecided instead of guessed.

You review what it found.

Check, simulation, and report show the falsified claims, unverified prose, and open questions to settle with your team.

Checks and limits

What the checks
can tell you.

The checker is deterministic.

No LLM decides whether a model passes its structural checks.

Simulation has a defined scope.

A counterexample disproves a claim. A passing bounded search covers only the conditions searched.

Unknowns stay visible.

Some requirements remain in prose that the simulator cannot execute. Reports list them for review.

The application needs its own tests.

The current toolkit checks models. Automatic application conformance and runtime enforcement are not implemented.

Questions about Meant

Where Meant fits.

Why use a DSL instead of a requirements document?

Prose is a useful starting point. A model adds references, conditions, outcomes, and expectations that the checker and simulator can inspect. You can keep requirements in prose; reports identify what remains unverified.

Does Meant generate application code?

The current toolkit does not generate applications. The model is an input to engineering design and agent-assisted implementation. Engineers choose the architecture, stack, integrations, and operational tradeoffs.

Does a passing model mean my application is correct?

No. Structural checks and bounded simulation provide evidence about the model. Application tests, integration checks, and reviews must separately establish that the implementation follows the intended behavior.

Do product managers need to learn the whole language?

Start by reviewing the rules and scenarios with an engineer. Agents can help draft the syntax. You decide whether the model says what the business means.

Can I install Meant today?

Yes. Meant is a developer preview: install it with bun add -g meant-lang (Bun 1.4 or later). The source is on GitHub under the MIT license. Read the project status.
